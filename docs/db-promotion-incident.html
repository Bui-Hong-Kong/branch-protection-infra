DB promotion when things break

DNS can move users to region B. Promotion makes B the database writer. Mixing those up — or skipping fencing — is how you get split-brain.

Before the incident · who writes?

In active/passive multi-region, only one database accepts writes. The other is a replica applying the primary’s change stream.

Region A

Primary · writer

  • Accepts writes from the app
  • Source of truth for commits
  • Ships WAL / redo to replica
  • App “writer endpoint” points here
Replication → async
Region B

Replica · reader (or idle)

  • Read-only until promoted
  • Applies changes from A
  • May lag (this is your RPO)
  • Warm standby for promote
RPO
How much data you may lose

Transactions on A not yet applied on B when A dies. Async replica ⇒ seconds of risk, not zero.

RTO
How long until writes work again

Detect + fence A + promote B + point apps + verify. DNS failover alone is not full RTO for writes.

Incident timeline

Example: region A primary is gone (crash, network, AZ/region event). Traffic and data roles must both be handled — in a safe order.

01
Detect

Something is wrong

Health checks fail, alerts fire, or on-call sees errors. Confirm: is it “app only” or “DB writer dead / unreachable”? App-only ⇒ maybe no promote. Writer dead ⇒ promote path.

02
Decide

Declare failover · pick RPO you will accept

Check replica lag on B if you can. Huge lag ⇒ more data loss. Decision is deliberate: promote B, or wait for A if RTO allows.

03
Fence

Stop A from writing · before or with promote

Power off / stop Postgres / block SG / revoke writer DNS on A. Goal: A must not accept commits after B becomes primary. This step prevents split-brain.

04
Promote

Make B the new primary

Postgres: pg_promote / promote trigger file. Aurora Global: managed promote / detach & promote. B stops replaying and opens for writes.

05
Repoint

Apps use B as writer

Update writer endpoint (DNS CNAME, Secrets Manager, config, RDS Proxy target). Bounce or reload pools so connections leave A. Route 53 may already send HTTP traffic to region B — align DB with that.

06
Verify

Prove writes · measure loss

Insert a canary row, check /ready, confirm only one writer. Estimate RPO from last applied LSN / missing IDs. Record times for the postmortem.

Fence then promote · why order matters

Promotion without fencing is the classic failure mode: two writers, divergent data, ugly restore.

1

Fence old primary

Ensure A cannot take writes (stop instance, kill DB, SG deny 5432, remove from writer DNS).

2

Promote standby

B becomes read/write. Confirm pg_is_in_recovery() = false (or cloud console “primary”).

3

Repoint applications

Writer connection string / secret → B. Drain old pools. Health checks should require “I am writer” if needed.

4

Do not start A as writer again

When A returns, rebuild it as a replica of B, then plan failback. Never “just start Postgres on A.”

Split-brain · what goes wrong

Both A and B accept writes for a while. Each has commits the other never saw.

Anti-pattern

Promote B while A is still writable

Users (or cron jobs, or a cached DNS hit) still write to A. B gets new writes from failed-over traffic. Two histories.

Recovery is no longer “fail back” — it is merge, pick a winner, or restore from backup. That is why fencing is not optional.

Failback · returning home

Living on B is fine until you choose to return. Failback is a planned promote in reverse — not “turn A back on.”

1

Rebuild A from B

Basebackup / new replica / Aurora secondary — A must follow B as source of truth.

2

Catch up · lag ≈ 0

Wait until replication is healthy. Schedule a maintenance window.

3

Fence B briefly · promote A (or planned switchover)

Same rules: only one writer. Managed DBs often have “switchover” for planned failback.

4

Repoint apps + DNS to A

Verify, then leave B as replica again. Update runbooks with real timings from the drill.

Who is writer right now? Dashboard / pg_is_in_recovery / cloud “primary” — single source

Can A become writer accidentally? No — automation and humans blocked until rebuild
