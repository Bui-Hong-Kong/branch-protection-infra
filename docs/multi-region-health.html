Complete request flow

One user HTTPS request from start to response — how it travels through primary infrastructure, what the backup region is doing, and how the path changes after failover.

User→ DNS→ ALB A→ App A→ DB primary→ Response
01
Client

User opens the app

Browser or API client requests https://app.example.com/.... It only knows the hostname — not which region or EC2 will answer.

02
DNS · Route 53

Resolve name → primary region

Resolver asks Route 53. Failover policy sees health check on region A = Healthy, so the answer is region A’s entrypoint (ALB DNS name, or EIP in a cheap lab). Result is cached for the record’s TTL.

03
Region A · edge of VPC

TLS hits the ALB

Packet enters AWS in region A. The Application Load Balancer in public subnets (multi-AZ) terminates TLS (or passes through), matches a listener rule, and picks a target group.

04
Region A · ALB → targets

Only healthy app targets get the request

ALB already runs its own health checks on each instance/pod (/ready). Unhealthy targets are skipped. Traffic stays inside the VPC to private subnets via security groups — users never SSH to app nodes.

05
Region A · app

Application handles business logic

App authenticates, validates, and (for writes/reads) opens a connection to the database writer endpoint in region A — typically private IP / RDS in private subnets.

06
Region A · data

Primary DB serves; replica is updated async

Postgres / Aurora primary commits the change (or returns the read). Streaming / Aurora replication pushes WAL to region B’s replica in the background — not on the user request path, but it defines your RPO.

07
Return path

Response travels back the same way

App → ALB → internet → user. Region B’s ALB and app were not on this hop list. They stayed warm: deployed, health-checked, replica applying logs — ready if DNS flips.

User→ DNS→ ALB B→ App B→ DB (promoted)→ Response
01
Before the user request

Region A fails health checks

Route 53 (or AGA) keeps probing A’s /healthz. After interval × failure threshold, A is Unhealthy (app down, ALB 502s, network block, etc.). This happens on AWS’s schedule — not inside your VPC cron.

02
DNS · Route 53

Same hostname, new answer → region B

Failover record stops returning A. New DNS lookups get B’s ALB (or EIP). Clients still on cached TTL may hit A until cache expires — that is why TTL matters for RTO.

03
Region B · edge of VPC

User request lands on backup ALB

Same hostname from the user’s point of view. TLS and listener rules now run in region B’s VPC — a separate failure domain, not a warm standby process on A’s box.

04
Region B · ALB → targets

Healthy B targets take traffic

B’s ALB has been health-checking its own targets the whole time. Only ready app tasks in B’s private subnets receive the request.

05
Region B · data (critical)

Reads may work; writes need promote

DNS failover alone does not make B the DB primary. For writes: promote the replica (or use Aurora Global / similar), fence A so it cannot accept writes, then point the app at the new writer. Skipping fencing → split-brain.

06
Return path

Response from B · A stays out of the path

App B → ALB B → user. Region A may still be “running” in the console; it simply must not receive user DNS or act as writer until failback is deliberate and safe.

While primary is active

Region A (primary)

  • Serves 100% of user traffic (active/passive)
  • ALB spreads load across AZs / healthy targets
  • DB is the writer; commits are authoritative
  • Publishes replication to B continuously
  • Must pass Route 53 and ALB health checks
At the same time

Region B (backup)

  • Does not get normal user DNS (passive mode)
  • Stack is deployed & warm — same app version ideally
  • ALB still health-checks local targets (so B is ready)
  • DB is replica — applying WAL; lag = RPO risk
  • Route 53 may also check B so secondary is known-good

What travels with the request vs what does not

On the request path Off the request path (background)
DNS lookup → ALB → app → DB query → response Route 53 / AGA probes every 10–30s
ALB choosing a healthy target for this connection ALB target health polling all instances
App read/write to current DB endpoint Replication A → B; metrics; deploys to standby
Security groups / VPC routing for that hop DB promote / fencing (human or automation on failover)

Four layers of “healthy”

AWS runs the probes. You define what success means — mostly via /healthz or /ready, plus thresholds.

Layer 0

Your app endpoint

Return 200 only if this instance should take traffic (process up, DB reachable, optionally “I am writer”). Return 503 otherwise. This is the real metric.

Layer 1

ALB target health · in-region

ALB polls each instance/pod on a path you set. Unhealthy targets get no new requests. Other AZs in the same region can still serve. ALB does not fail over to another region.

Layer 2

Route 53 / Global Accelerator · cross-region

External checkers hit the region entrypoint (ALB or public URL). After N failures → mark region unhealthy → DNS/anycast sends users to the other region.

Layer 3

Data plane · separate decision

DNS moving traffic ≠ promoting Postgres/Aurora. Writer fencing and replica promote are runbooks (or managed global DB). Avoid dual-primary split-brain.

Component Scope You set Effect
ALB target group Instance / pod Path, codes, interval, thresholds Drop bad targets in-region
Route 53 health check Region entrypoint URL, interval, failure threshold Flip DNS to other region
Global Accelerator Regional endpoint Similar health config Steer anycast IP

How a constant health check works

Example: Route 53 every 30s, failure threshold 3. You do not run the cron — AWS (or Cloudflare) does.

Healthy

Connect OK + status in success range (e.g. 2xx), enough times in a row → keep primary DNS.

Unhealthy

Timeout, connection fail, or non-success status × failure threshold → failover to secondary.

Knobs you set on the AWS check

Knob Meaning Lab start
Protocol / path What to call HTTPS · /healthz
Request interval How often AWS probes 30s (or 10s)
Failure threshold Fails in a row → Unhealthy 3
DNS TTL How long clients cache the old IP 60s (dominates RTO)

Rough RTO ≈ (interval × failures) + TTL. Example: 30×3 + 60 ≈ ~2–3+ minutes, not instant.

Cheap EC2 lab vs production

Same mental model. Production adds VPC shape, ALB, and multi-AZ — not a different idea of health.

Cheap lab

  • Default VPC · public EC2 + EIP
  • One box = app + maybe Postgres
  • Route 53 health → failover DNS
  • No NAT / ALB needed to learn
  • Manual / scripted DB promote

Production

  • Custom VPC · public ALB, private apps
  • ALB + ASG/EKS multi-AZ in each region
  • Route 53 or AGA for region steer
  • Aurora Global / DDB global / rehearsed promote
  • Game days · measured RTO/RPO
